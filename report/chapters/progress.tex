\chapter{Work in Progress: The Dev Tracks}
\label{ch:progress}

On 6 November Hani asked for independent dev tracks, started from a stable version
of the function whose numbers are comparable to TAMPURA's (\BF{68}). The session
``Go'' orchestrates them. Each track has one responsible session, which reports to
its parent when its job is done; the parent then archives that conversation
(\BF{68}). On 8 November at about 15:45 Hani announced that the current state would
be presented to the supervisor, asked that the tracks come to a halt, that big things
be brought to an end and that exploratory ones be cut, and named that state
Checkpoint 1 (\BF{68}). At the checkpoint no track starts a batch, a probe, an
evaluation or a cluster job; a step that was running ends and is recorded; and nothing
is merged into the trunk (\ID{tracksstate}{tracks state file}). The state of each
track below is the one at the checkpoint, from the checkpoint table of the tracks
state file (written at 15:56 on 8 November) and from the track's own files; a later
fact is given with its time. Where the files disagree, \Cref{sec:disagreements} says
so.

\section{The Stable Base and the Rules}
\label{sec:tracks-base}

The base is the tag \texttt{stable-2026-11-06} on commit d6a9715 of the branch
\texttt{tampura-bridge}. Its pipeline code is what run 2 of the generated-scene
evaluation measured, so its numbers are those: ours 57 of 80, TAMPURA 46 of 80, four of
its episodes crashed, pairs 20 to 9, exact McNemar $p = 0.061$ (with a scene as the unit
10 to 5, $p = 0.30$) (\BF{68}, \ID{recount}{recount of 14 November}). \validitynote{failures (4 of 80)} On the laptop the tag passes 130
unit tests and 89 bridge tests (3 skipped), solves seed 0 in 36 seconds and a
generated seed (106) in 60 seconds; its known failures are \BF{64} and \BF{65}
(\BF{68}). Each track works on its own branch and in its own copy of the checkout;
only the orchestrator merges into the trunk (\BF{68}).

The rules that every track follows, as the tracks' state file words them
(\ID{tracksstate}{tracks state file}):
\begin{itemize}
  \item Simulation batches take a lock, one at a time, with a hold of at most
  about 30 minutes (rule 7).
  \item Tracks launch agents of the Sonnet or Haiku class only (rule 9).
  \item Every deviation from a TAMPURA task or setup is approved by Hani in writing
  in chat before anything that rests on it is run or merged; code may be prepared
  meanwhile (rule 12).
  \item Tracks put no window on Hani's desktop; GUI features are checked off screen
  (rule 13).
  \item From 13:25 on 7 November the tracks started no batch in WSL. The laptop was low on memory
  (4.4 of 30.8\,GB of memory free, 54.5 of 60.2\,GB of commit charge at 13:20), and
  Hani's words were read by Go as: run nothing in WSL until the memory problem is
  found and fixed. Path 12's report did not establish a cause (\BF{69}). Go lifted
  the freeze on 8 November at 14:07 on Hani's word, with the virtual machine capped
  at 8\,GB and with guards: a memory check before every batch, no new batch above
  85\,\% of the commit limit, a memory log during it, and a wait of 70 seconds after a
  start timeout (rule 14).
  \item Before any evaluation of one environment and planner against another, Hani
  confirms by eye on at least four seeds, two per system, and the evaluation goes
  ahead only after Hani's approval (rule 15, \Cref{sec:visual-check}).
  \item Since 14:40 on 7 November, runs must not build up memory: one process per
  episode, each episode's peak memory and the free memory at its start and end
  recorded, and a batch stops after the current episode when less than 4\,GB is free
  (rule 16).
  \item A session that Hani compacts often stays idle afterwards, so its parent sends
  it one message to wake it (rule 17).
  \item Since 8 November every evaluation records, per episode, the drops and collisions
  and how each was detected, and reports print clean success (no drop and no collision)
  beside success; Hani picks the headline criterion once the first counts are in
  (rule 18).
\end{itemize}

\paragraph{TB-23, the drop of a held box.} Hani reported on 8 November at about 14:15,
as top priority, that in Hani's runs of our arm the held box was dropped repeatedly
and the run still recovered. The runs were seeds 3 and 4 of path 5's scene (two
occluders, goal holding), watched in the GUI (\TK{3}). GUI runs record no
telemetry, so path 3 counted from the simulator's truth before every action: one drop
in each run, in each case of the green box, so 2 drops in 3 carries of occluders over
the two runs; the target is never carried, because the goal is holding and its pick
ends the episode (\TK{3}). Both runs succeeded: in seed 3 the target became visible when the box was
lifted, and in seed 4 the replan moved the other occluder; each drop cost a carry and
a replan of 7 to 10 seconds and left a box on its side (\TK{3}). Headless probes found
two causes: 24 episodes on seeds 3 and 4, with the simulator's state logged every 0.01
seconds, then 28 more on seed 2 and in a batch that measured the wall time (\TK{3}):
\begin{enumerate}
  \item \emph{The carry's jerks swing the box out of the grip.} The arm streams every
  waypoint pair at a constant joint speed with no acceleration limit, so at each
  junction the hand's speed drops from 0.60 to 0.11\,m/s in one frame (58\,m/s$^2$).
  Each jerk swings the box, whose weight hangs 55 to 60\,mm below the middle of the
  strip of about 16\,mm that the pads hold, until it levers the fingers apart. The
  switch \texttt{carry\_trapezoid} of \BF{59}, one acceleration-limited schedule per
  held move, is the candidate cure: it removes the jerks. In the batch that ran both
  settings on seeds 0 to 5 (two repetitions; seed 1 builds no scene, so 10 episodes
  each), the four-fix set of \BF{59} lost the box in 3 of 10, 2 to the swing and 1 to a
  collision; with the switch added in 1 of 10, to a collision ($p = 0.63$). A held move
  takes 0.39 seconds in both settings, so no cost per carry is measurable. The A/B on
  seeds 0 to 19 with three arms (the four-fix set, the set with the switch, and the base
  without the fixes) ran on 12 November: a lost-grip record in 20 of 48 episodes without
  the switch and in none of 48 with it (seeds 1, 8, 12 and 14 build no scene;
  \ID{recount}{recount of 14 November}). Whether the switch becomes a default is Hani's
  call after Hani's visual check of seeds 3 and 4 with and without it.
  \item \emph{The carried box hits an object the robot has not seen.} The carry's
  motion check treats unknown space as free, so on seed 4 the box strikes the hidden
  target at about 1\,m/s in every setting; the four-fix set then loses the box and
  the base setting keeps it and shoves the neighbouring box by 130 to 140\,mm. A second
  case, with a box the robot knows (seed 2, the one carry of 12 that needed a
  random-tree path), shows the trapezoid schedule following the path with a rest at the
  bend, and the carried box hitting the other occluder, which the check lists as an
  obstacle, toppling it and leaving the hand. This cause goes to path 14.
\end{enumerate}
Two further findings follow. The four-fix set of \BF{59}, which brought the die to no
loss in 60 carries, loses these tall boxes where the base setting keeps them (seed 3:
3 of 3 against 0 of 3 in the first probe, 2 of 3 against 0 of 3 in the A/B of 12
November), so the board's owed check of that set on our own scenes fails
on this scene. And the telemetry takes a gripper opened past 35\,mm for an opening
one, so a drop caused by a strike has no lost-grip record, which rule 18's drop count
must not inherit (\TK{3}).

\section{Path 12: Why WSL Wedged}
\label{sec:path12}

On 7 November every attempt to start WSL ended in a start timeout between 11:02 and
11:08, and Hani's rule 14 then froze all WSL work until it was known why the machine
runs out of memory. Path 12 read the Windows side only, apart from two tests of its own health-check script before rule 14 reached it, and
ranks each statement as measured, read or unverified (\BF{69}, \TK{12}). The cause of
the wedge is not established. The virtual machine, 117 hours old, stopped answering as a

of its life, in 37 periods of the laptop's standby, and the failure came at most 63
minutes after the last resume. That makes a fault around the laptop's modern standby the
best-supported class, with the trigger unproven (\BF{69}). Two readings fail: no
session's call started the wedge, and the shutdown command did not end it; WSL's own
idle teardown did (\BF{69}). Windows never ran out of memory in the records, but sat at
81 to 94\,\% of its commit limit, with 56.4 of 60.2\,GB at the highest reading; the
Claude sessions and the desktop app hold 36\,\% of the standing base of about 47\,GB, and
the WSL virtual machine is the swing, 13.3\,GB committed at 12:24 during runs
(\BF{69}). The report proposes a memory cap, giving memory back, evidence for the next
wedge, and rules for the tracks. The cap (8\,GB) and the rules are in place as rule
14's guards; the other proposals are not recorded as done, and the report's questions
wait for Hani (\BF{69}).
