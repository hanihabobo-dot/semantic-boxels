\label{sec:tracks-base}

The base is the tag \texttt{stable-2026-11-06} on commit d6a9715 of the branch
\texttt{tampura-bridge}. Its pipeline code is what run 2 of the generated-scene
evaluation measured, so its numbers are those: ours 57 of 80, TAMPURA 46 of 76, pairs
18 to 9, exact McNemar $p = 0.122$ (\BF{68}). On the laptop the tag passes 130
unit tests and 89 bridge tests (3 skipped), solves seed 0 in 36 seconds and a
generated seed (106) in 60 seconds; its known failures are \BF{64} and \BF{65}
(\BF{68}). Each track works on its own branch and in its own copy of the checkout;
only the orchestrator merges into the trunk (\BF{68}).

The rules that every track follows, as the tracks' state file words them
(\ID{tracksstate}{tracks state file}):
\begin{itemize}
  \item Simulation batches take a lock, one at a time, with a hold of at most
  about 30 minutes (rule 7).
  \item Tracks launch agents of the Sonnet or Haiku class only (rule 9).
  \item Every deviation from a TAMPURA task or setup is approved by Hani in writing
  in chat before anything that rests on it is run or merged; code may be prepared
  meanwhile (rule 12).
  \item Tracks put no window on Hani's desktop; GUI features are checked off screen
  (rule 13).
  \item Since 13:25 on 7 November nothing runs in WSL. The laptop was low on memory
  (4.4 of 30.8\,GB of memory free, 54.5 of 60.2\,GB of commit charge at 13:20), and
  Hani's words were read by Go as: run nothing in WSL until the memory problem is
  found and fixed (rule 14). Path 12 has since delivered its report to Go, and the
  freeze still held at 16:07 (\ID{tracksstate}{tracks state file}).
  \item Before any evaluation of one environment and planner against another, Hani
  confirms by eye on at least four seeds, two per system, and the evaluation goes
  ahead only after Hani's approval (rule 15).
  \item Since 14:40, runs must not build up memory: one process per episode, each
  episode's peak memory and the free memory at its start and end recorded, and a batch
  stops after the current episode when less than 4\,GB is free (rule 16).
\end{itemize}

\section{Path 2: Which TAMPURA Tasks Give a Quick Result}
\label{sec:path2}

Hani asked which of TAMPURA's other tasks could give a first number within a few
working days on which the accuracy is neither zero nor that of chance (\TK{2}).
Path 2 delivered on 6 November. Its ranking is that two tasks give a quick result,
both through our planning layer on TAMPURA's execution functions: class\_uncertain
first and slam\_collect second; \fdice-simple is a smoke test, and tool\_use and
puck\_slide are not quick (\TK{2}). The tool\_use task needs 4 to 6 days and
puck\_slide 13.5 to 17 working days to a result, the track estimates (\TK{2}). The
results are in \Cref{tab:published-cu} and \Cref{tab:published-sl}, with the check
against the published numbers. The track states that neither task exercises our
perception or physical execution, and that any claim from them must say so
(\TK{2}). It also found two faults outside our own code: TAMPURA's class\_uncertain
applies a motion plan that failed (TB-19 of the board, \TK{3}), and the planner
library's translator needs a cost function defined for every tuple of objects (TB-18,
\TK{3}).

The track's questions Q40 to Q45 are partly answered. Hani's answer was to implement
both tasks even though the perception is TAMPURA's, since boxelization still has to
be used somehow; this made mode S count and led to path 7 (\TK{2}, \BF{68}). The use of
TAMPURA's object models inside mode S is accepted and declared, the world-state test
is primary (\BF{68}). TAMPURA on class\_uncertain over seeds 0 to 19 on the cluster
(about 3.4 hours at the laptop's mean, the track estimates) and what the paper may
say from mode S runs are open (\TK{2}).
