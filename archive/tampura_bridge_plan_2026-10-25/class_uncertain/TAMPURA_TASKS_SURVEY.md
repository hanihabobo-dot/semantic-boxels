## 1. class_uncertain  (paper task A "Class Uncertainty")

Goal and reward. Put every object that might still be a fruit into the bowl, and break nothing. Coded reward (class_uncertain/env.py:466-472): ForAll objects o: (possible-fruit(o) implies exists region r: on(o,r) and is-bowl(r)) and not broken(o). Evaluated on the abstract BELIEF, 0 or 1 (tampura/spec.py:140-143), not on the physical world. An object stops needing a move only when inspect has zeroed all its fruit-class mass (env.py:97-103, 115-118).
Objects. Panda, floor/table, 3 movable YCB objects plus one bowl (YCB "bowl", scale 1.5) in all 20 saved scenes. Fruit classes apple, lemon, strawberry; ball classes tennis_ball, racquetball, baseball (env.py:30-31, 40). Objects get mass 0.1, gravity -10, then 2000 settle steps (env.py:302-303, 334-337). The hidden variable is the class label, not the location: every object starts with a UNIFORM prior over all 6 classes (env.py:50-53), regardless of what the scene holds.
Uncertainty type. Semantic class (and, through it, grasp/drop risk).
Actions (env.py:414-464). inspect(o): moves the arm to a gripper pose 0.1 m above the object (env.py:153-173) and returns the TRUE class from the simulator (env.py:175-177); precondition not holding, possible-fruit, not broken. During planning (state None) the class is sampled from the belief (env.py:148-149). pick(o,g,r): depends on is-fruit(o) (env.py:418); preconditions not holding, object-grasp, not broken, on(o,r); stochastic outcome: with probability DROPABILITY[class] the observation is "broken" (0.0 for fruit, 0.85 for balls, env.py:33-37, 226-229). The comment at env.py:33-34 says 0.35 was used for "risk sensitivity experiments" and 0.85 "for faster runtime", so the published numbers may have used another value (UNVERIFIED). The "break" is a random.random() draw, NOT a physical drop (the pick motion already ran, state.grasp stays set, panda_env_utils.py:963). drop(o,g,r): needs is-bowl(r), places at 0.1 m above the bowl frame (env.py:237-241), opens the gripper, steps the world 200 times with sleeps (env.py:260-262), and the belief asserts on(o,bowl) regardless of where the object lands (env.py:94-95, 443). grasp-sample stream from the saved grasp library (env.py:272-284, 404-412).
Observation model. ClassUncertainObservation (detected_object, class_label, grasp, grasp_object, broken; env.py:133-138). Inspect is noise free (exact class). No pose uncertainty: poses are read from the world by body id (env.py:153, 190). No rendering at all. Execution is the shared kinematic one: carry is an attachment re-assigned every motion step (panda_env_utils.py:611-639), headless trajectories teleport (927-930), pick/place motion plans use no obstacles (env.py:192, 208).
Scenes and seeds. 20 saved JSON scenes in class_uncertain/problems/ (categories, poses, scales); chosen by random.choice(os.listdir(...)) after random.seed(global_seed) (env.py:354-364), relative path, so the run must start in the repo root, and the seed-to-scene map depends on os.listdir order (same trap as find_dice). Generator env_generator.py:43-108: NUM_PROBLEMS 20, 1 to 3 fruits (random.randint(1,3)) and the rest balls so that there are 3 objects, bowl last, x in [0.3,0.7], y in [-0.4,0.4], random yaw, rejection-sampled for no overlap. I tabulated the 20 files with grep: 7 scenes have 1 fruit, 6 have 2, 7 have 3; every scene has exactly 3 movable objects + 1 bowl.
Config (env_configs/class_uncertain.yml): max_steps 20, batch_size 20, num_samples 500, flat_sample true, flat_width 3, symk top_k / bd.
Paper. Task A. Published (Table I, N=20): TAMPURA return 0.87+-0.01 (best baseline BayesOpt+WAO 0.78+-0.06, eps-greedy 0.69, MLO 0.66, Q-learning 0.42, None/MCTS/DQN 0.00); per-step time 28+-26 s; executed steps 6.44+-1.21; abstract beliefs visited 118.06+-14.12. NOTE: 0.98^6.44 = 0.878, so a return of 0.87 is consistent with near 100% success (my arithmetic, UNVERIFIED as the paper's method). MISMATCH repo vs paper text: the paper (Sec. VI-A, App. C1) says 2 to 10 objects, at least one bowl, and classification NOISE added to ground-truth labels; the repo has 3 objects, a uniform prior and an exact reveal. Which version produced Table I is UNVERIFIED.
Fit for Hani's pipeline: PARTIAL. Same Panda, same PyBullet world, same YCB assets, same kinematic executor and the same bridge hooks as find_dice (TampuraEnv with self.state and self.sim_world, env.py:373-375), and the world is physical (gravity, mass 0.1), which suits his physical execution. But the uncertainty is object identity, not occlusion, so his shadow/region machinery is not exercised. Missing: (1) a class belief and an inspect sense action that returns a label (the label comes from the simulator, so no vision is needed; his camera/segmentation pipeline would not help); (2) a bowl as a place region and a "drop into the bowl" goal; (3) the risk model: balls break with prob 0.85 as a coin flip, which has no physical counterpart, so a physical pick of a ball either needs the same coin flip imposed (a bridge-only rule he has said he does not want) or is scored by what physically happens; (4) a scoring channel: the reward reads the belief, and one terminal observation cannot carry several objects (the observation holds ONE detected_object and one grasp). A conservative rule "inspect, then pick only known fruit" is a trivial plan for a classical planner and would probably match or beat TAMPURA's return, but that also means the task does not stress what his method is for. Rough effort: 1 to 2 weeks (belief + sense + bowl region + scoring adapter + YCB fruit/ball grasps).

## 2. tool_use  (paper task B "Pose Uncertainty")

Goal and reward. Stack the three cubes into a tower: reward = on(cube0,cube1) AND on(cube1,cube2) (tool_use/env.py:719-724; the hook is the last object and is excluded by range(len-2)). Evaluated on the abstract BELIEF: on() is computed from the belief's mean positions of the particle sets, com1.z > com2.z + BLOCK_SIZE/4 and xy distance < BLOCK_SIZE (env.py:167-173). The physical world is not read for the score.
Objects. Panda, extended table (table AABB lengthened by 0.5 m in x, env.py:228-238), 3 cubes (BLOCK_SIZE 0.02 = half extent, so 4 cm cubes, mass 0.1, panda_env_utils.py:548-572) and a hook (URDF models/misc/hook/hook.urdf, env.py:222-225) fixed at (0.1,-0.35,0.02) yaw -30 deg (env.py:268-271). Gravity -10 (env.py:308).
Uncertainty type. Object pose. Each cube is a cloud of NUM_PARTICLES = 10 "ghost" cubes drawn from a Gaussian with std INITIAL_STD 0.02 m in x and y around the cube's mean (env.py:32-36, 182-219, 276-290); ghosts collide only with the floor and hook, not with each other (collision masks env.py:247-255). The hook pose is known. A cube counts as known-pose when the robust std of its particles is below KNOWN_POSE_STD 0.01 m in all axes (env.py:33, 164).
Actions (env.py:643-717). pick(o,g): needs known-pose(o), nothing on or under o, hand empty. place(o,p,g,r): sets known-pose(o); the belief writes the commanded pose p as the new pose (env.py:562-564). stack(o1,g1,o2): needs a known-pose or already stacked o2; writes the commanded stacked pose into the belief (env.py:457-459). pull-towards(hook,g,o2): needs the hook in hand and NOT known-pose(o2); its only stochastic outcome is verify_effects = known-pose(o2) (env.py:703-715): the hook sweeps a hard-coded trajectory about the target mean (env.py:320-344) and the belief re-simulates the sweep on its ghost particles with 5 physics steps per waypoint (env.py:102-121, 153-154), so particles that get funnelled into the hook corner collapse. The paper's point (App. C2): use the hook to bring objects into reach and to align them into its corner. No sensing action exists at all ("without a wrist camera", Sec. VI-A).
Observation model. HookObservation(conf, grasp, grasped_obj, hook_traj, poses) (env.py:63-68): the observation is the COMMANDED hook trajectory or the commanded placement pose, replayed by the belief; the executing world's cubes are never read back. In the executing world the hook sweep is physical (apply_sequence with sim_steps 5, env.py:410-416), picks and places use the shared kinematic attach (GhostSceneState attaches the grasped body and its ghosts, env.py:39-54). Hence the score is a function of the simulated belief, not of what physically happened. Grasps come from the mesh, not the saved library (env.py:462-475).
Scenes and seeds. NO saved problems. initialize() draws 3 cube means uniformly (x in [0.4,0.7], y in [-0.3,0.3], z 0.02) until the minimum pairwise distance exceeds 10*INITIAL_STD = 0.2 m (env.py:580-586), then builds the executing world and a separate sim world from the same means (env.py:588-589) with independent particle draws (np.random.normal), so the seed alone fixes the scene (random and numpy seeded in run_planner.py). 20 seeds = 20 different scenes, no layout reuse.
Config (env_configs/tool_use.yml): max_steps 20, batch_size 20, num_samples 300, flat_sample false, flat_width 10, pwa 0.5, symk unordered / bd, from_scratch FALSE (only task besides prob_occ/toy_discrete without a rebuild of the model each step; tampura/policies/tampura_policy.py:100-105).
Paper. Task B. Table I: TAMPURA 0.66+-0.07; BayesOpt+WAO 0.70+-0.07 and MLO 0.65+-0.07 are equal or better (the paper says determinized planning suffices here because failures are recoverable and the observation branching is binary); eps-greedy 0.58; None 0.13+-0.04; Q-learning, MCTS, DQN 0.00. Per-step time 21+-13 s; executed steps 9.69+-0.68; abstract beliefs visited 27.81+-10.53 (Table III).
Fit for Hani's pipeline: NONE. The task is defined by NOT having perception: his rendered-depth perception would measure the cube poses and erase the uncertainty, and with perception switched off his system has no pose belief, no known-pose notion, no tool grasp and no hook sweep. What it needs: particle pose belief, a non-prehensile hook action, a stack action, and a scoring rule that reads the belief (physical stacking would be a different, incommensurate criterion; a physical blind pick of a 4 cm cube with 2 cm std might even succeed without the hook). Rough effort: weeks to months, mostly non-comparable.

## 3. puck_slide  (paper task D "Physical Uncertainty")

Goal and reward. Get a puck into the goal region at the far end of a shuffleboard-like slab: reward = in(puck, goal0) (puck_slide/env.py:745). in() is true when the corners of a 2 cm box around the believed puck pose lie inside the goal box (test_in, env.py:660-672; goal box 0.2 m deep and 0.7 m wide, GOAL_AABB env.py:54-56). The believed puck pose is the OBSERVED pose of the real puck after each push (env.py:540-545), so this is the one task whose reward is tied to a physical readback.
Objects. Panda on a custom slab world (floor 1.1 m x 0.7 m, stool, thin surface slab, an "ik" region where the robot stands the puck; env.py:39-82, 260-333), no table scene and no YCB. Puck: cylinder radius 0.06 m, height 0.04 m, mass 1 (env.py:33-34, 73, 236-245). Gravity -9.8 (env.py:258). Only goal0 is used (GOAL_OBJECTS has one entry, env.py:74).
Uncertainty type. Physical parameter: the puck's lateral friction. True value random.uniform(0.05, 0.15) (env.py:63-64, 681); the slab has 0.1 (FRICTION_MID, env.py:314). Belief: 20 particle pucks whose friction is drawn uniformly in 1/friction between 1/0.05 and 1/0.15 (env.py:66, 353-356), i.e. skewed towards low friction, while the true value is uniform in friction, weights updated by a Gaussian likelihood (cov 1e-3 I) of each particle's final xy against the observed xy, then resampled with jitter (env.py:156-196). known-friction holds when the weighted std is below 0.01 (env.py:144). off-table is an absorbing failure (env.py:151-152).
Actions (env.py:718-743). push-to(puck, region): needs the puck in the ik region; depends on known-friction; verify_effects in(puck,region) and known-friction. Controller shoot_controller (env.py:422-512): plans a Cartesian end-effector push, repeated pc_steps = 5 times with a proportional correction of the push effort (KP 0.01) from the median final x of the real puck plus the ghost particles; in the EXECUTING world each trial resets the real puck to its start pose first (env.py:493-509), so only the last trial's pose is the result. nudge(puck, d): a gentle push (effort 0.005, 5 steps) in a sampled direction (Normal(0,0.02) x Normal(0,0.3), normalised to 0.2 m, env.py:654-657) whose only stochastic outcome is known-friction. No grasping, no pick/place, no hidden object.
Observation model. PuckObservation(puck_pose, joint_path, effort, unreachable) (env.py:101-105): the exact pose of the real puck after the push (no sensor noise); the belief re-simulates the same joint path on its particles and reweights them (env.py:209-229). Execution is genuinely physical (joint-motor controller via follow_path/simulate_controller plus 2000 settle steps, env.py:384-415), the only task in the repo whose robot motion is dynamic rather than a teleport.
Scenes and seeds. One fixed geometry, no saved problems; only the true friction (and particle draws) vary with the seed through Python random (env.py:681, 354). 20 seeds = 20 friction values.
Config (env_configs/puck_slide.yml): max_steps 20, batch_size 10, num_samples 20, flat_sample true, flat_width 20, symk top_k / bd.
Paper. Task D. Table I: TAMPURA 0.52+-0.11; best baseline is DQN 0.47+-0.09 (the paper notes MCTS and DQN do relatively well here because the horizon is only 1 to 4 controller executions); eps-greedy 0.42; None and Q-learning 0.34; MLO 0.29; WAO and MCTS 0.24. Per-step time 23+-7 s; executed steps 3.75+-1.79; abstract beliefs visited 5.00+-0.00 (Table III). Rough ceiling check: 0.98^3.75 = 0.93, so 0.52 would imply roughly 56% success if failures score 0 (my arithmetic, UNVERIFIED).
Fit for Hani's pipeline: NONE. No objects to find or grasp, no perception, no pick/place/sense; the decision is "calibrate friction with a nudge or push now". His deterministic PDDLStream planner has no way to represent a hidden friction; at best a B9-style port (his loop around THEIR push controller) would reduce to "push, observe, replan", losing his contribution. Missing: friction particle belief, push and nudge controllers, the slab world. Rough effort: 2 to 3 weeks and not informative for hidden-object search.

## 4. slam_collect family  (paper tasks E-M "SLAM with manipulation" and E-MF "manipulation-free")

Registered envs: slam_collect (slam_collect/env.py:1215), slam_collect_simple (:1538), slam_collect_custom (:1556); registration :1607-1609. A fourth config slam_collect_1p.yml exists with NO registered env (KeyError on get_env, tampura/tampura/config/config.py:20-21); what "1p" means is UNVERIFIED (maybe one particle).
World. Pure 2D Python/matplotlib simulation, NO PyBullet, NO Panda, no physics: a 10 m x 10 m plane (ENV_SIZE 10, env.py:49), rectangular robot 0.3 x 0.6 m (:47), start pose (1,1,1 rad) (:1335), goal square (0.8 x 0.8 m) at (8,8) (:48, 1227-1231), 4 corner points (:1301-1315). slam_collect: 5 random rectangular obstacles (sides 0.3 to 0.6 m, random yaw, rejection sampled), 5 beacons (physical 0.4 m, "vision" square 2.0 m, :43-46) and 3 yellow target blocks 0.5 x 0.5 m (:1217-1219, 1245-1299).
Uncertainty type. Robot localisation (SLAM): every motion step adds Gaussian noise std 0.04 m to delta x and delta y (ACTION_STD, env.py:50, 647-652); the robot pose is a 20-particle belief (num_particles=20, :1216) that counts as known_pose when the x and y variances are both below 0.05 (:53, 214-218). Obstacle, beacon, target and goal poses are known. Localisation is restored by move_look (drive into a beacon's vision square, then the true pose is returned) or move_corner (drive into a clamped corner) (env.py:303-306, 365-367, 1152-1212).
Actions (env.py:1405-1511). move_pick(t), move_place(t,r), move_to(r), move_look(beacon), move_corner(c), no-op. Paths come from an RRT on the mean particle with zero noise (:1071-1141); each action's verify_effects are the outcomes of the noisy rollout (holding, known_pose, in(r), target_in, in_collision). Observation: SlamObservation(regions_in, holding, robot_pose only when looking at a beacon or corner, collision) (:60-72). The executing "state" is the same 2D simulator with one noisy sample (:340-342, 363-369).
Reward. slam_collect (E-M): all three targets in the goal region and no collision (get_goal, env.py:1525-1535, REGION_IN_THRESH 0.8 on the particle fraction, :56, 264-271). slam_collect_simple (:1538-1553): 20 obstacles instead of 5, reward = robot reaches the goal region without collision (targets unused). slam_collect_custom (:1556-1604): empty world, one beacon at the centre (5,5), no obstacles, no targets, no corners, same goal-only reward; its yml uses gamma 0.95 not 0.98.
Scenes and seeds. No saved problems; everything is drawn with np.random in generate_initial_state (:1245-1299) after np.random.seed(global_seed), so a seed fixes the map. Custom is fully deterministic apart from motion noise.
Config (env_configs/slam_collect*.yml): max_steps 20, batch_size 20, num_samples 200, flat_sample false, flat_width 1, symk unordered / bd.
Paper. E-M = slam_collect: TAMPURA 0.81+-0.02 (eps-greedy 0.74+-0.06, WAO 0.56, MLO 0.41; None, Q-learning, DQN 0.00, MCTS 0.03); per-step time 129+-55 s, the slowest of all tasks; executed steps 9.22+-3.84; beliefs visited 68.67+-26.56. E-MF: TAMPURA 0.95+-0.00, MLO and WAO and None also 0.95, eps-greedy 0.93, Q-learning 0.93, MCTS 0.92, DQN 0.55+-0.10; per-step time 31+-11 s; executed steps 1.20+-0.51; beliefs visited 50.70+-9.26. Which repo env is E-MF is UNVERIFIED; slam_collect_simple fits the 50.7 visited beliefs better than the empty custom map, but custom fits "used to verify baselines" better.
Fit for Hani's pipeline: NONE. 2D mobile-base localisation with no manipulator, no 3D scene and no hidden object; the only shared ingredient is symbolic planning. A port means rewriting his planner's world model from scratch (particle pose belief, noisy 2D kinematics, beacon re-localisation); nothing of his perception, shadows or physical execution applies. Effort: months, no scientific link to hidden-object search.

## 5. find_dice_simple  (not in the paper)

Subclass FindDiceEnvSimple(FindDiceEnv) (find_dice/env.py:1016-1029), registered at :1033. It overrides only get_scene_data: a hard-coded scene with ONE die (category "dice") at xyz (0.6257, 0.0, 0.0209) and a fixed quaternion, no cups, no saved file (docstring: "Only contains a single die in a reachable area"). ## 7. Cross-cutting facts added after the per-task pass

- Only find_dice renders images: grep for get_image/camera/segmentation/render gives 47 hits in find_dice/env.py and 0 in class_uncertain, tool_use, puck_slide, slam_collect (env.py of each). The other four tasks have no perception code; their observations are symbolic (true class, commanded poses, true puck pose, region membership).
- Where the reward is computed: find_dice, class_uncertain, tool_use and slam_collect score their own belief (for class_uncertain the on() fact comes from the drop action's arguments, env.py:94-95, and "broken" from a random draw; for tool_use from commanded poses and replayed particles; for slam_collect from the fraction of particles inside a region, REGION_IN_THRESH 0.8). puck_slide is the exception: its belief stores the observed pose of the real puck (puck_slide/env.py:540-545).
- Which tasks have gravity/dynamics in the executing world: class_uncertain (gravity -10, mass 0.1, 2000 settle steps, 200 steps after a drop; env.py:302-337, 260-262), tool_use (gravity -10, cubes 0.1 kg, hook sweep stepped 5 times per waypoint; env.py:308, 416), puck_slide (gravity -9.8, mass-1 puck, motor-controlled arm; env.py:258, 384-415). find_dice has no setGravity and never steps physics (Hani's audit P4.2); slam_collect has no physics at all. Carrying is the same kinematic attachment everywhere (panda_env_utils.py:611-639, GhostSceneState tool_use/env.py:39-54).
- Scene provenance by file-name epoch (the generators name files str(time.time())): class_uncertain problems were generated 2023-11-26 03:29:52-59 UTC (before the paper's first version, March 2024), so they may well be the paper's scenes (UNVERIFIED); find_dice problems 1747173590/91/93 were generated 2025-05-13 21:59:50-53 UTC, SEVEN months after the paper's v2 (Oct 2024), so the shipped find_dice layouts are probably NOT the ones behind Table I (UNVERIFIED).
- find_dice/env_generator.py:44-181 runs an endless loop that writes one new scene JSON per iteration (1 to 5 inverted cups from a_cups_ud..e_cups_ud, the die placed at a cup's point, accepted only if the die is absent from the wrist-camera segmentation at DEFAULT_ARM_POS, 20 retries), so more hidden-die layouts than the 3 shipped can be made cheaply with the same executor. The paper's "2 to 10 objects" is larger than the generator's 2 to 6 bodies.
- Bridge reuse: tampura_bridge/ is find_dice specific: task_spec.py hard-codes find_dice categories, mesh extents, masses, inertia, the fixed eye, workspace window and pick contact floor, each measured and cited to a BF# entry; scoring.py imports find_dice.env.SceneObservation and builds ONE terminal observation (one held symbol, joint readback); policy.py appends one boxel_episode action. class_uncertain's belief takes one detected_object per observation and learns bowl membership only from an action named "drop" (class_uncertain/env.py:94-95, 133-138), so the one-episode harness cannot be reused as is: a class_uncertain port needs either B9 (his planner choosing inspect/pick/drop executed by THEIR execute_fns) or a per-step harness.
